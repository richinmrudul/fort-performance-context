# Fort Performance Context Product Demo

Updated: 2026-09-01

## 1. Information Hierarchy

The demo is a read-only, post-workout product view. It intentionally does not show
any pre-workout prediction, readiness score, recovery score, warning, or training
recommendation.

The primary hierarchy is:

1. Today's post-workout handgrip result.
2. Difference from expected performance from prior personal history.
3. Recent personal trend.
4. Session context recorded for the study observation.
5. Methodology, data limits, and timing caveats.

## 2. Screen And Component Set

The frontend uses a restrained editorial sequence:

- Result hero: privacy-safe athlete/session label and percent of expectation.
- Supporting metrics: actual value, Track A expected value, neutral difference,
  and prior observation count.
- Performance trend: lightweight SVG trend with actual handgrip and Track A
  expectation when available. Early observations show limited-history states.
- Descriptive context: sleep, caffeine, wellness, match, and actigraphy values
  shown as reference facts with shared timing caveats.
- Transparency: model/data limits and future production data needs in a
  secondary semantic disclosure.

## 3. Source Files Powering Each View

- `data/processed/track_a_features.csv`: actual handgrip outcomes, prior-only
  history fields, primary modeling row flag, source-row order, and trend rows.
- `reports/track_a_predictions.csv`: row-level Track A expected performance for
  `model_name == "prior_expanding_mean"` and the exact selected observation.
- `reports/track_a_metrics.json`: Track A evaluated sample counts, model-input
  manifest, row-order policy, and benchmark metrics.
- `data/processed/track_b_features.csv`: existing processed descriptive context
  joined to primary Track A-eligible observations.
- `reports/model_comparison.json`: Track B comparison result showing contextual
  models did not improve over Track A prior-history expectation.
- `reports/track_b_timing_audit.json`: timing classifications and missing
  metadata used to label all context as descriptive only.

The frontend reads only `frontend/public/data/demo.json`, generated by
`python3 -m src.demo.build_demo_data`.

## 4. Metric Formulas

Track A reports `prior_expanding_mean` as the trusted comparison used in the
current model comparison, so the demo uses that value as expected performance.
The repository does not establish a separate athlete baseline distinct from this
expectation; UI copy therefore says "expected from prior personal history."

- Actual performance: `data/processed/track_a_features.csv:handgrip_kg`.
- Track A expected performance: `reports/track_a_predictions.csv:y_pred_handgrip_kg`
  where `model_name == "prior_expanding_mean"` and the evaluation row matches
  the selected `observation_id`.
- Expected-performance identity check:
  `y_pred_handgrip_kg == data/processed/track_a_features.csv:prior_expanding_handgrip_mean`.
- Percent of expectation:
  `actual_percent_of_expected = handgrip_kg / y_pred_handgrip_kg * 100`.
- Difference from expectation: `difference_kg = handgrip_kg - y_pred_handgrip_kg`.
- Difference percent: `difference_percent = actual_percent_of_expected - 100`.
- Sample size: `prior_valid_handgrip_count`.
- Trend history: all valid handgrip rows for the selected athlete from
  `track_a_features.csv`, sorted by `athlete_row_index` and labeled by
  observation sequence rather than fabricated calendar dates.

The existing `target_pct_prior_median_baseline` remains a modeling target/audit
field and is not used as the hero percentage because the chosen Track A expected
performance is the evaluated `prior_expanding_mean`.

## 5. Deterministic Athlete And Session Selection

The default session is selected by a neutral rule:

1. Start with `data/processed/track_b_features.csv`.
2. Keep rows where `is_primary_modeling_row` is true, `handgrip_kg` is present,
   `prior_expanding_handgrip_mean` is present, and
   `prior_valid_handgrip_count >= reports/track_a_metrics.json:minimum_prior_valid_handgrips`.
3. Join to the Track A `prior_expanding_mean` prediction for the same
   `observation_id`.
4. Sort by `raw_daily_row_index`, then `observation_id`.
5. Select the last row.

This selects the latest eligible observation with sufficient prior personal
history, not the best performance or most favorable model result.

## 6. Missing And Limited-History States

The data adapter and UI support these states:

- No prior observations: "More personal history is needed."
- Fewer than the Track A minimum prior observations: "Limited prior history."
- Missing actual result: "Not available for this observation."
- Missing expected value: "Expected value not available."
- Missing context field: "Not available for this observation."
- Context present with ambiguous timing: "Timing not verified."
- No defensible date: x-axis uses "Observation" and sequence labels.
- Incomplete trend history: trend rows keep null expectations and explanatory
  labels rather than substituting zero.

## 7. Context Timing Language

Context is descriptive, not predictive. Accepted labels include:

- "Context recorded for this study observation."
- "Timing relative to performance was not available."
- "Shown for reference, not used in the trusted prediction."
- "Timing not verified."
- "Shown descriptively."

The UI must not claim that sleep, caffeine, wellness, match context, or
actigraphy predicted, explained, caused, improved, or reduced performance.

## 8. Desktop And Mobile Layout

Desktop around 1440 px uses a spacious product surface:

- Top emphasis: editorial result hero.
- Middle emphasis: actual-versus-expected metrics and personal trend.
- Lower emphasis: descriptive context, followed by methodology disclosure.
- Sections use whitespace and subtle dividers instead of dense boxed panels.

Mobile around 375-390 px uses a single column:

- Hero metrics first.
- Trend next with horizontally safe SVG scaling.
- Context cards and methodology last.
- No horizontal overflow; long values wrap or use compact numeric formatting.

## 9. Visual System

The visual direction is premium wearable-product, serious, and evidence-oriented:

- Warm off-white foundation.
- Near-black text with muted secondary copy.
- One restrained green accent for result emphasis.
- Subtle dividers, little shadow, and restrained 8 px radius only where framing
  helps readability.
- Large, clean display typography with generous vertical rhythm.
- Lightweight SVG charting.
- No stock photography, medical imagery, arbitrary gauges, excessive gradients,
  glassmorphism, dense card grids, or demotivating failure treatment.
- Color is never the only indicator; labels and signs are always present.

## 10. Accessibility Approach

- Semantic headings and landmark structure.
- Buttons/links have visible focus states.
- Trend SVG includes accessible labels and a tabular fallback-style summary in
  nearby text.
- Color contrast is checked against the dark foundation and off-white surfaces.
- Motion is minimal; any animation respects `prefers-reduced-motion`.
- Missing and timing states are text labels, not color-only states.
